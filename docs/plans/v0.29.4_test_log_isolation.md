# v0.29.4 Plan: Test Log Isolation

## Context

After v0.29.2 (execution-mode safety), bot.log still showed entries from both the real bot
process (pid=784) and the test suite (pid=29880) in the same log file. The executor fix
eliminated the live-mode contamination risk, but the log file still accumulated test-injected
entries that looked alarming in production triage.

Root cause: `config.py` hardcodes `LOGS_DIR = BASE_DIR / "logs"`. When `utils/logger.py` is
imported (which happens transitively for most test files via `trading/executor.py` ->
`utils/logger.py`), all path constants and directory-creation logic run at import time against
the real `logs/` tree. Module-level singletons (`_app_fh`, `_err_fh`) are then lazily
initialized on first `get_logger()` call, all pointing to `logs/app/bot.log`.

## Non-Obvious Design Decisions

### pytest_configure, not a fixture

The isolation must be in place BEFORE any test module is imported (module-level code runs at
import time). A session-scoped autouse fixture runs too late -- the import-time code in
`config.py` and `utils/logger.py` has already executed by then.

`pytest_configure(config)` fires before collection, which means before any test file is
imported. This is the only pytest hook that reliably precedes all module imports in the test
process.

### Env var in config.py, not logger.py

The override is added to `config.py` because `LOGS_DIR` is the single source from which all
subdirectory constants in `utils/logger.py` are derived. One change in `config.py` redirects
the entire log tree with zero changes to `utils/logger.py`.

### Runtime default is unchanged

`_log_root_env = os.environ.get("KALSHI_LOG_ROOT", "")` with a falsy check means:
- `KALSHI_LOG_ROOT` not set (normal bot run): `LOGS_DIR = BASE_DIR / "logs"` -- identical to before
- `KALSHI_LOG_ROOT` set to non-empty string (test run): `LOGS_DIR = Path(override)`

There is no way to accidentally activate the override during normal bot operation without
explicitly setting the env var.

### No singleton reset needed

Because `pytest_configure` sets the env var before any test module imports, `config.py`
computes the correct temp `LOGS_DIR` on first import. `utils/logger.py` imports `LOGS_DIR`
from config and derives all subdirectory constants at that point -- all pointing to the temp
dir. File handler singletons are lazy (created on first `get_logger()` call) so they too
initialize against the temp dir. No module reload or singleton teardown is required.

## Runtime-Log Cleanliness Verdict

After this change, a pytest session:
- Sets `KALSHI_LOG_ROOT` to a temp dir before any module imports
- All `config.LOGS_DIR`, `logger.APP_LOG_FILE`, `logger._LOG_APP_DIR` etc. resolve to the temp dir
- `_app_fh` and `_err_fh` singletons initialize against the temp dir
- `logs/app/bot.log` is never opened or written during any test run
- Temp dir is removed automatically on test session exit (`pytest_unconfigure`)
