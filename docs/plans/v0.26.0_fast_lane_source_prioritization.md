# v0.26.0 Plan: Fast-Lane Source Prioritization + Match Quality Suppression

## Context

All current paper trades entered at market_yes_price=50.0 -- Kalshi's default quote before
any trading activity. Edge comes from base-rate mispricing (events objectively not 50%
likely, but priced 50/50).

Root cause analysis identified the dominant limiters:
1. **LLM prompt bias**: systematic zero-output (Phase 3 of roadmap -- not this plan).
2. **Source prioritization flat**: `_source_priority()` had only 2 tiers. Wire services
   treated identically to slower aggregators.
3. **No match quality suppression**: Borderline-score candidates with single-token overlap
   were reaching LLM analysis, burning inference time on clearly wrong markets.

This version implements three phases:

- **Phase 1**: Fast-lane source queue prioritization
- **Phase 2**: Match quality in daily report
- **Phase 3**: Conservative low-quality match suppression + observability

---

## Phase 1: Fast-Lane Source Prioritization

### What was built

`SOURCE_PRIORITY_TIERS: dict[str, int]` added to `config.py` after
`EARLY_MAX_NEWS_AGE_BY_SOURCE`. Mirrors exact same lookup pattern.

`_source_priority()` in `main.py` expanded from 2-tier (Reddit=2, everything=1) to
3-tier (Tier1=wire services, Tier2=RSS default, Tier3=Reddit) with case-insensitive
fallback.

### Non-obvious design decisions

- **AP not added**: AP feeds are configured in RSS_FEEDS but the source string that
  appears on `NewsItem.source` (from `parsed.feed.title`) was never observed in
  trades.jsonl history. Added comment; add when confirmed from live logs.
- **Reddit moves 2->3, not a new priority**: Preserves relative ordering between Reddit
  and RSS while creating room for tier-1 fast lane. Existing non-wire RSS unchanged.
- **Debug log for tier-1**: `[FAST_LANE]` DEBUG log emitted per tier-1 enqueue.
  Lets operator confirm tier-1 sources are actually receiving priority.

## Phase 2: Match Quality in Daily Report

### What was built

`_match_quality_report_section()` in `trading/paper_trader.py`. Reads `trades.jsonl`
at report time, counts `MATCH_DIAGNOSTIC` records, computes low-quality rate, top flag
reasons, and top flagged tickers.

### Non-obvious design decisions

- **All infrastructure was already present**: `log_match_diagnostic()`, `_match_quality_flags()`,
  and `scripts/match_quality_diagnostics.py` were implemented in a prior session. The only
  gap was surfacing the data in the daily report.
- **Inline JSON reading**: Report reads trades.jsonl directly rather than importing from
  `scripts/`. Keeps import direction clean (scripts/ is for operator tools, not library code).
- **Includes KXTEST records**: Report counts ALL MATCH_DIAGNOSTIC events including test
  synthetic records. The `--exclude-test` flag in `scripts/match_quality_diagnostics.py`
  filters these; the report intentionally does not, to show the full picture.

## Phase 3: Conservative Low-Quality Match Suppression

### What was built

Config-gated suppression block in `analysis/market_matcher.py`:
- `ENABLE_LOW_QUALITY_MATCH_SUPPRESSION` (default off) -- actual suppression
- `ENABLE_MATCH_SUPPRESSION_DEBUG` (default off) -- observability only

Suppression criteria (all three must hold):
1. `near_threshold_score`: score within 0.02 of min_score
2. `minimal_overlap` OR `single_named_entity_only` in heuristic_flags
3. (implied by 1+2: `low_match_quality` is True)

New logger methods:
- `log_match_suppressed()` -- emits `MATCH_SUPPRESSED` event
- `log_match_suppression_candidate()` -- emits `MATCH_SUPPRESSION_CANDIDATE` event

### Non-obvious design decisions

- **Suppression lives in `find_candidates()`**: Quality flags are already computed there.
  No return type change needed; no changes to callers. The suppression `continue` simply
  prevents the candidate from being appended to `scored`.
- **`MATCH_DIAGNOSTIC` always logged before suppression check**: Every candidate is
  observable regardless of suppression state. The diagnostic log fires unconditionally;
  suppression fires after.
- **`_meets_suppression_criteria` extracted as shared local**: Both the debug log and the
  suppression block evaluate the same boolean. Extracting it prevents divergence.
- **Debug flag fires regardless of suppression flag**: An operator can enable debug logging
  while suppression is still off, accumulate `MATCH_SUPPRESSION_CANDIDATE` events, review
  them, and only then enable suppression. This is the intended validation workflow.

### Live validation finding

First `MATCH_SUPPRESSION_CANDIDATE` in production:
- Headline: "Iran War Live Updates: U.S. to Blockade Ships From Iranian Ports"
- Ticker: KXTRUMPIRAN-26MAY01
- Score: 0.0753, matched_tokens: ["iran"]
- Flags: near_threshold_score, single_named_entity_only, minimal_overlap

**Verdict: would have been a false positive suppression.** The market IS about Iran; the
headline IS about Iran. Token mismatch (blockade/ships/ports vs. deal/negotiations) drove
the weak score, not topic mismatch.

**Implication for criteria refinement (Phase 3.1)**: Before enabling suppression, add a
fourth condition: the single matched named entity must NOT appear as a substring of the
market ticker. `any(token in market.ticker.lower() for token in matched_tokens)` -- if
True, the market's primary subject matches the headline's subject, so pass through.
