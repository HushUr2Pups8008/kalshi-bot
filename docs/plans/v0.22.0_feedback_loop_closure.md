# v0.22.0 -- Feedback Loop Closure

## Context

After v0.19-0.21 added four feedback loops (price-driven search, keyword outcome
recording, position drift logging, subreddit quality + discovery), a comprehensive
audit found that several loops were broken at the "read" end: data collected but
never consumed to change future decisions.

**Key finding**: The biggest broken loop was `keyword_outcomes` -- written at every
resolution since v0.19.0 but zero code ever read from it. This was the "Phase 3"
referenced in a paper_trader.py comment that was never implemented.

Additional gaps found: 7 schema columns missing from `paper_trades` that blocked
analytics; raw LLM outputs not stored; match_score not flowing through the pipeline.

---

## Broken Loops Closed in This Release

### CRITICAL -- Data collected, loop now closed

**1. Keyword Outcomes Table (Highest Impact)**
- `keyword_outcomes` table: `(trade_id, ticker, series_ticker, keyword, direction, market_side, resolved_yes, correct, ts)`
- Written at every resolution since v0.19.0. Zero code read from it.
- Fix: `analysis/keyword_stats.py` -- `KeywordStats` class loads per-(keyword, series_ticker)
  accuracy at startup, refreshes every 6h. `get_multiplier()` returns [0.5, 1.5] multiplier
  applied in `_keyword_score()`. MIN_SAMPLES=10 required before any effect.

**2. Schema Gaps**
- `series_ticker` buried in `market_snapshot` JSON blob -- now a real column, backfilled.
- `resolved_ts` -- now populated in `resolve_market()`.
- `signal_type` -- "news" | "price_fade" | "fade_tweet" -- tagged at construction.
- `match_score` -- Jaccard score at match time -- flows through full pipeline.
- `llm_direction`, `llm_magnitude`, `llm_confidence` -- raw LLM outputs now persisted.

### HIGH -- Computed but not fed back

**3. Match Score**
- Jaccard similarity computed in `find_candidates()` but dropped after return.
- Fix: flows into `SignalAnalysis.match_score`, persisted to `paper_trades`.
- `scripts/performance_analysis.py` section 7d shows win rate by score band with
  advisory if empirical data suggests a better `PAPER_MIN_MATCH_SCORE` threshold.

**4. LLM Raw Fields**
- `_parse_llm_response()` extracted direction/magnitude/confidence but discarded them.
- Fix: returned from `estimate_probability()` as 7-tuple, stored in `paper_trades`.
- Enables future LLM calibration analysis in performance_analysis.py.

## What Does NOT Change

- `REDDIT_CORE_SUBREDDITS` -- always polled, exempt from all quality gates.
- Existing keyword lists in `config.py` -- base strengths unchanged; multiplier
  is a multiplicative layer on top.
- Source credibility system -- unchanged; KeywordStats is a parallel mechanism.
- LLM calls -- unchanged; keyword multipliers only affect the keyword scoring path.
- Go-live gates -- min_edge, win_rate, drawdown thresholds unchanged.

## Non-Obvious Design Decisions

**Why per-(keyword, series_ticker) accuracy?**
"ceasefire" is predictive for Ukraine/Russia markets but noisy for Middle East.
Aggregating across all series dilutes signal. The existing `keyword_outcomes`
schema already captures `series_ticker` -- we just need to read it.

**Why multiplier range [0.5, 1.5] matching source_credibility?**
Continuous range avoids cliff-edge suppression. A keyword with 40% accuracy on
a series gets 0.9x (slight penalty) not 0.0x (full suppression). Matches the
pattern the bot already uses -- less cognitive load to reason about.

**Why MIN_SAMPLES=10?**
Below 10 samples, accuracy estimates are noisy enough to mislead (a 2/3 run
would give 67% accuracy and a 1.17x multiplier from pure luck). 10 is conservative
but appropriate for the current trade volume. Re-evaluate at 200+ resolved trades.

**Why advisory-only for edge/match thresholds?**
Auto-changing thresholds on small samples risks overfitting. Advisory logs surface
the information for human review without acting.

**Why defer drift re-analysis (Loop C) to Mac Studio?**
At 20-40s per LLM call on CPU, a drift event during an active news cycle blocks the
Ollama queue. Mac Studio (GPU) reduces this to <5s. The logging infrastructure is
already in place -- the action layer just needs fast inference.

**Why store resolved_ts without backfilling historical?**
Historical trades need an API call per trade to find resolution timestamp (Kalshi
doesn't expose batch resolution history easily). NULL for old trades is acceptable;
analytics improve organically as new data accumulates post-v0.22.0.

## Verification

1. After schema migration (first bot run):
   ```sql
   PRAGMA table_info(paper_trades);
   -- Should show: series_ticker, resolved_ts, signal_type, match_score,
   --              llm_direction, llm_magnitude, llm_confidence
   ```

2. After backfill:
   ```sql
   SELECT count(*) FROM paper_trades WHERE series_ticker IS NOT NULL;
   -- Should match existing trades that have market_snapshot JSON set
   ```

3. KeywordStats loading (check bot.log at startup):
   ```
   [KEYWORD_STATS] Loaded N (keyword, series) accuracy pairs from keyword_outcomes
   ```
   N=0 is fine initially -- will grow as more trades resolve.

4. Verify signal_type populated:
   ```sql
   SELECT signal_type, count(*) FROM paper_trades GROUP BY signal_type;
   -- Should show: news, price_fade (and fade_tweet if feed active)
   ```

5. After 24h -- match_score populated on new trades:
   ```sql
   SELECT count(*) FROM paper_trades WHERE match_score IS NOT NULL;
   ```

6. After 7+ days with >= 10 keyword outcomes per pair:
   ```
   python scripts/performance_analysis.py
   -- Section 7c shows keyword accuracy table
   -- Section 7d shows match score win rate by band
   -- Section 7b shows per-series win rate
   ```

7. After sufficient data -- keyword multipliers diverge from 1.0:
   ```sql
   SELECT keyword, series_ticker, count(*), avg(correct)
   FROM keyword_outcomes
   GROUP BY keyword, series_ticker
   HAVING count(*) >= 10
   ORDER BY count(*) DESC LIMIT 20;
   ```
