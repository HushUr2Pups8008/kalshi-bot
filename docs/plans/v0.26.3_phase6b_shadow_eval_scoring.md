# v0.26.3 Plan: Phase 6B -- Shadow Eval Promotion-Readiness Scoring

## Context

Phase 6A (v0.26.2) added `scripts/keyword_shadow_eval.py` which reads
`ANALYSIS_REJECTED(reason=no_keywords)` miss events and reports raw hit counts, source/ticker
coverage, concentration risk, and phrase overlap for a small handpicked set of shadow phrases.
The report was a flat list with no guidance on which phrases were ready to promote.

Phase 6B adds a transparent, explainable scoring system and groups the report output by
recommendation bucket, so the output is immediately actionable without manual calculation.

**Current live data (35 miss events, 3 shadow phrases):**
- strait hormuz: 9/35 hits (25.7%), 2 sources, 4 tickers, 44% concentration, 6 overlap hits
- hormuz blockade: 5/35 hits (14.3%), 2 sources, 4 tickers, 40% concentration, 3 overlap hits
- blockade iran: 3/35 hits (8.6%), 1 source, 3 tickers, 33% concentration, 3 overlap hits

**What Phase 6B adds:**
1. `score_phrases()` -- pure, testable function that adds `score`, `bucket`, `reason` to each phrase
2. `overlap_hits` per phrase in `evaluate_phrases()` output
3. Grouped report sections by bucket (PROMOTE CANDIDATES / CONTINUE SHADOWING / REJECT FOR NOW)
4. 11 new tests in `TestScorePhrases`

## Architecture

### What was NOT changed
- `load_miss_corpus()`, `_phrase_matches()`, `_tokenize()` -- no I/O changes
- `evaluate_phrases()` -- only addition is `overlap_hits` field per phrase
- No live runtime code touched

### New functions
- `score_phrases(phrase_results)` -- pure, in-place, returns phrase_results
- `_print_phrase_block(pr, total, max_examples)` -- extracted helper, called per phrase in grouped loop

### Data flow
```
load_miss_corpus() -> evaluate_phrases() -> score_phrases() -> print_report()
```
`score_phrases` is called in `main()` between `evaluate_phrases` and `print_report`.
`build_json_result` also includes the new fields.

## Scoring Formula

All factors are explicit and explainable:

```
score = hits * 4
      + unique_sources * 6    # source diversity weights more than raw hits
      + unique_tickers * 3    # multi-market utility
      - 10                    # concentration penalty (if top ticker fraction >= 0.50)
      - overlap_hits * 2      # overlap penalty (shared hits add less unique value)
```

**Why these weights:**
- Sources weighted highest (6x) because multi-source coverage is the strongest signal that a phrase
  is capturing real editorial attention across newsrooms, not one prolific outlet.
- Tickers (3x) reward multi-market utility. A phrase useful for 4 open markets is more broadly
  valuable than one useful for a single market (which will expire).
- Concentration penalty (-10) is a hard binary, not a continuous penalty, because the issue
  is qualitative: a phrase tied to one market loses all value when that market expires.
- Overlap penalty (-2 per overlap hit) is soft -- some overlap is fine; it just means the phrase
  adds less unique coverage relative to the other shadow phrases.

## Bucket Rules (Conservative)

```
promote candidate:   score >= 20 AND hits >= 5 AND sources >= 2 AND NOT concentration_flag
continue shadowing:  hits >= 1 (but not eligible to promote)
reject for now:      hits == 0
```

**Why conservative:** False positives in live keywords cause real signal noise and wasted LLM
calls. The thresholds are set to require clear evidence (multi-source, multi-ticker, meaningful
hit rate) before promoting. `continue shadowing` is the safe holding state for phrases that show
promise but have not yet accumulated enough evidence.

## Non-Obvious Design Decisions

- **`overlap_hits` is per-phrase, not global.** For phrase P, `overlap_hits` = number of events
  where P matched AND at least one other evaluated phrase also matched. This is computed from
  `event_phrase_hits` after the main loop in `evaluate_phrases()`. The denominator for overlap
  fraction (if needed in future) is that phrase's own `hits`, not `total_miss_events`.

- **`score_phrases` modifies dicts in place AND returns the list.** In-place mutation keeps the
  main data structure consistent (callers don't need to swap references); the return value makes
  it chainable and testable without side-effect awareness.

- **Bucket groups are ordered by urgency (promote -> shadow -> reject).** The operator reading
  the report sees actionable items first. REJECT FOR NOW is last because it only needs attention
  when the phrase set is being pruned, not on routine runs.

- **`_print_phrase_block` extracted as a helper.** The grouped loop calls it once per phrase.
  Avoids duplicating the per-phrase formatting code across bucket sections.

- **Score and bucket are NOT part of the JSON report's top-level structure.** They live in
  `phrase_results[*].score/bucket/reason` -- same as the text report. The JSON consumer can
  group by bucket if needed. Keeping scoring inside phrase objects rather than as a separate
  top-level section makes the JSON self-contained per phrase.
