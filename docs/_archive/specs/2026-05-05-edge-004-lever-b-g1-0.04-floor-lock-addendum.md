## 1. Why lock now (vs after Lever A's verdict)

Parent spec §11 deferred the harness pre-load on two grounds:

1. **"The constants depend on Lever A's outcome — if A closes EDGE-004, Lever B never lands and the harness is dead code."**
2. **"The exact floor value is sized post-OBS-003 (per §4) and may be 0.04, 0.03, or 0.025; pre-loading the harness against the wrong value creates a false-positive xpass at landing time."**

Both grounds are weakened by 2026-05-05 evidence:

**Re #1:** the Wave-2 A.1+ branch decision table (`docs/governance/2026-05-05-wave-2-a1plus-branch-decision-table.md`) sequences Branch A → C → D over a worst-case 42 d wall-clock. The probability that Lever A closes EDGE-004 in the FIRST 14 d (Branch A passive observe) is bounded above by the historical legal-niche conversion rate, which is sparse. Even if A closes EDGE-004, a pre-loaded but unused xfail harness is at most a 2-line `pytest.mark.xfail` removal at marker-cleanup time — not "dead code" in any meaningful sense.

**Re #2:** Codex's counterfactual (the empirical sizing) puts the candidate floors at 0.05 / 0.04 / 0.03 / 0.025. The spec §3 recommendation "start at 0.04" reflects the conservative-loosening-first principle (half-step landing for blast-radius control). 0.03 / 0.025 are deferred-secondary candidates per spec §3. Locking 0.04 doesn't preclude a future Lever B-2 spec for 0.03 — it just commits to the first step.

**Net:** the harness deferral was right at 2026-05-03 (Codex's counterfactual was fresh). At 2026-05-05 the empirics are stable and the operator's deploy sequence is locked enough to pre-load the harness without measurable risk.

**Required test cases:**

```python
# tests/test_lever_b_g1_floor_lock.py
import pytest

@pytest.mark.xfail(strict=True, reason="LOCK: G1=0.04 lands in Wave-3 ≥ 2026-06-06; xpass on deploy commit triggers marker removal in same hunk")
def test_g1_confidence_threshold_locked_at_0_04():
    """LOCK: tasks/trade_readiness_gate.py:G1_CONFIDENCE_THRESHOLD must equal 0.04 post-Lever-B-deploy."""
    from tasks.trade_readiness_gate import G1_CONFIDENCE_THRESHOLD
    assert G1_CONFIDENCE_THRESHOLD == 0.04, (
        f"Lever B floor expected 0.04; got {G1_CONFIDENCE_THRESHOLD}. "
        "If this floor was sized to a different value (0.03 / 0.025 / etc.), "
        "the LOCK addendum needs a revision before landing."
    )

@pytest.mark.xfail(strict=True, reason="LOCK: G1 failsafe = 0.08 (2× primary) lands with G1=0.04")
def test_g1_failsafe_threshold_locked_at_0_08():
    """LOCK: G1_FAILSAFE_CONFIDENCE_THRESHOLD must equal 0.08 (2× the primary 0.04 floor)."""
    from tasks.trade_readiness_gate import G1_FAILSAFE_CONFIDENCE_THRESHOLD
    assert G1_FAILSAFE_CONFIDENCE_THRESHOLD == 0.08, (
        f"Lever B failsafe expected 0.08 (2× primary 0.04); got {G1_FAILSAFE_CONFIDENCE_THRESHOLD}."
    )

@pytest.mark.xfail(strict=True, reason="LOCK: 2× ratio between failsafe and primary preserves regime-uncertainty headroom")
def test_g1_failsafe_to_primary_ratio_is_2x():
    """LOCK: failsafe = 2 × primary (preserves the regime-uncertainty headroom from the original spec)."""
    from tasks.trade_readiness_gate import (
        G1_CONFIDENCE_THRESHOLD,
        G1_FAILSAFE_CONFIDENCE_THRESHOLD,
    )
    assert G1_FAILSAFE_CONFIDENCE_THRESHOLD == pytest.approx(2 * G1_CONFIDENCE_THRESHOLD), (
        f"failsafe-to-primary ratio expected 2.0; got "
        f"{G1_FAILSAFE_CONFIDENCE_THRESHOLD / G1_CONFIDENCE_THRESHOLD:.3f}."
    )
```

**Why three tests, not one:** the locked invariants are conceptually distinct. (a) primary floor; (b) failsafe floor; (c) the 2× ratio invariant. A future Lever B-2 spec might lower the primary to 0.03 while preserving the 2× ratio (failsafe → 0.06); the third test catches a ratio break independent of the absolute value tests.

**Strict-xfail rationale:** the parent spec §6 acceptance criteria require all three constants update in the same commit. Strict-xfail enforces that all three xpass simultaneously on the deploy commit; partial deploys (e.g., primary updated but failsafe forgotten) are caught by the strict-xfail framework.

**Marker-removal hunk:** the Lever B deploy commit must remove the `@pytest.mark.xfail` decorator from each test in the same hunk as the constant edit. Per `wave-1-changelog-entry-prestaged.md` precedent, this is the standard pattern.
