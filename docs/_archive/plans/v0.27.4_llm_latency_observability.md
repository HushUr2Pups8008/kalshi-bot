# v0.27.4 Plan: LLM Latency Observability

## Context

After the v0.27.1/v0.27.2 fixes (remove `repetition_penalty`, correct `OLLAMA_MODEL`), Ollama
inference calls started succeeding consistently. The next diagnostic gap was: even though the
LLM path was working, there was no way to know whether inference was fast or slow -- whether
CPU-only qwen2.5:7b was a latency bottleneck in practice.

The v0.27.3 audit confirmed that the dominant historical failure mode was `model_not_found`
(deterministic config error), not CPU contention. But now that the LLM path is healthy, the
open question is: what does per-call latency look like under real traffic? The daily review
showed LLM success rate but not latency.

---

## What Changed

### `analysis/signal_analyzer.py`
- `_llm_meta()`: added `latency_ms: int | None = None` parameter; included in returned dict.
- `_ollama_estimate_detailed()`: added `t0 = time.monotonic()` before the `try:` block.
  Latency captured at each return path:
  - HTTP error: captured after reading the response body
  - Success: captured after `data = await resp.json()`
  - `ClientConnectorError`, `TimeoutError`, `JSONDecodeError`, `ValueError`, `Exception`:
    each except block computes `latency_ms = int((time.monotonic() - t0) * 1000)`
- `_anthropic_estimate_detailed()`: `t0` placed before `try:`, latency captured after
  `client.messages.create()` returns, or in the general `except Exception` handler.
  `ImportError` leaves `latency_ms=None` (no real call was attempted).
- `estimate_probability()`: all three `log_signal_analysis_detail()` call sites pass
  `llm_latency_ms=llm_meta.get("latency_ms")`. When LLM was never attempted (keyword-only
  path where Ollama was circuit-open before the call), `latency_ms` is `None` and the field
  is omitted from the JSON record.

### `utils/logger.py`
- `log_signal_analysis_detail()`: added `llm_latency_ms: int | None = None` kwarg.
  Written to the record only when not `None` (conditional, preserves backward compatibility
  with records that pre-date this version).

### `scripts/signal_edge_diagnostics.py`
- `summarize()` SIGNAL_ANALYSIS_DETAIL parsing: reads `llm_latency_ms` into `detail_rows`.
- `llm_observability` dict: added `latency_ms_samples: list[float]`.
- Aggregation loop: appends `row["llm_latency_ms"]` to samples when not `None`.
- New `_p95(values)` helper: uses `statistics.quantiles(n=20)[18]` for the 95th percentile;
  returns `None` for < 2 samples (not enough to compute).
- New `fmt_latency_stats(samples)` helper: renders
  `avg=Xms  median=Xms  p95=Xms  max=Xms  n=N` or `n/a` if empty.
- `print_summary()`: added `LLM latency` line in the LLM Path Observability section.

### `scripts/daily_review.py`
- Section 3 (ANALYSIS): added `LLM latency` line after `LLM fallback to keyword`, pulling
  from `llm_obs.get("latency_ms_samples", [])` via `signal_edge_diagnostics.fmt_latency_stats()`.

## Non-Obvious Design Decisions

- **`latency_ms` omitted from JSON when None, not written as `null`**: Preserves backward
  compatibility. Historical records don't have the field; diagnostic scripts use `.get()`
  and treat absence as no data, not zero.

- **Timer placed before `try:` in Ollama path**: The `try:` block covers all exception paths.
  Placing `t0` before it means even a `ClientConnectorError` (connection refused) gets a
  latency value -- useful for confirming the connection attempt was fast (< 1ms) vs slow
  (firewall timeout).

- **Anthropic `ImportError` leaves `latency_ms=None`**: If the `anthropic` package is not
  installed, no real I/O attempt was made, so there is no meaningful latency to record.
  The `t0` is placed before `try:`, but the `ImportError` handler intentionally omits it.

- **`latency_ms_samples` includes failed attempts**: Timeout rows (60s), HTTP error rows,
  parse error rows are all included in the samples. This is intentional: you want to see
  p95 inclusive of failures to understand the tail latency that actually affects users, not
  just the happy path.

- **p95 via `statistics.quantiles(n=20)[18]`**: stdlib only, no numpy. For n=20 quantiles,
  index 18 (0-based) is the 95th percentile cut-point. Returns `None` for < 2 samples
  (the stdlib function requires >= 2 data points).
