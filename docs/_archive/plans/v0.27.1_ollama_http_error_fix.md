# v0.27.1 Plan: Fix Dominant LLM Failure Mode (ollama_http_error)

## Context

v0.27.0 added LLM observability fields to `SIGNAL_ANALYSIS_DETAIL` events in `trades.jsonl`.
First inspection of the new data revealed two failure modes in equal proportion (3 events each):

| Status | Count | Root Cause |
|--------|-------|------------|
| `ollama_unavailable` | 3 | Ollama process not running at time of signal (infrastructure) |
| `ollama_http_error` | 3 | Ollama process running but returning non-200 from `/v1/chat/completions` |

`ollama_unavailable` is a pure infrastructure issue -- Ollama wasn't started. Cannot be fixed in
code; circuit-breaker already handles it correctly.

`ollama_http_error` is actionable. All 3 events were from the same source (NYT > World News) at
12:22 UTC. Manual curl of the endpoint confirmed Ollama was healthy at the time of investigation.
The inference payload contained `"repetition_penalty": 1.05` -- a native Ollama `/api/generate`
field that is NOT part of the OpenAI Chat Completions spec. Ollama's compat layer returns HTTP 422
for unrecognized fields, silently blocking all inference attempts on that endpoint.

---

## Fix

Two changes to `analysis/signal_analyzer.py`:

### 1. Remove `repetition_penalty` from the OpenAI-compat payload

**Before:**
```python
payload = {
    "model": cfg.ollama_model,
    "messages": [...],
    "max_tokens": 256,
    "temperature": 0,
    "repetition_penalty": 1.05,   # <-- non-standard field
}
```

**After:**
```python
payload = {
    "model": cfg.ollama_model,
    "messages": [...],
    "max_tokens": 256,
    "temperature": 0,
    # repetition_penalty removed -- not a valid OpenAI Chat Completions field
    # Use "options": {"repeat_penalty": 1.05} on native /api/generate if needed later
}
```

### 2. Upgrade `ollama_http_error` log from DEBUG to WARNING

Before: `log.debug("Ollama returned HTTP %d", resp.status)` -- invisible in production.
After: reads response body, logs at WARNING with status code + first 200 chars of body.
This makes future non-200 responses diagnosable without enabling DEBUG mode.

---

## Non-Obvious Design Decisions

- **`repetition_penalty` vs `repeat_penalty`**: Ollama uses `repeat_penalty` (not `repetition_penalty`)
  in its native `/api/generate` endpoint. Even that native spelling goes in `options: {}` not the
  top-level payload. The misspelled non-standard field in the compat endpoint silently blocked all
  inference.

- **Body read wrapped in try/except**: `await resp.text()` can fail if the connection drops between
  the headers check and body read. The outer exception path already handles that; the inner try
  ensures the happy path continues to the WARNING log even on a body-read failure.

- **`ollama_unavailable` not addressed in code**: The circuit-breaker (3 failures -> 5-min blackout)
  already handles repeated unavailability. The 3 occurrences were from a single Ollama restart window,
  not a persistent failure. No code change warranted.

---

## Verification

1. 376/376 tests pass (no behavior change -- payload field removed, no logic touched)
2. No non-ASCII in runtime-emitted strings
3. Manual curl `POST http://localhost:11434/v1/chat/completions` with the new payload (no
   `repetition_penalty`) returns HTTP 200 -- confirmed endpoint accepts the cleaned payload
4. Future `ollama_http_error` events will now appear as WARNING in `logs/app/bot.log`
   with status code and response body, enabling root-cause diagnosis without DEBUG logs
