# v0.29.2 Plan: Execution-Mode Safety Hardening

## Context

Bot log showed alarming entries: `[LIVE] Placing order: KXTEST-25DEC31`, multiple
`[LOSS_LIMIT] Session start balance recorded` lines with different balances in the same second,
and both `GO-LIVE confirmed` and `Paper trading phase started` appearing in the same log file.

Root cause: two processes writing to the same `bot.log` simultaneously -- the running bot (pid=784,
paper mode) and the test suite (pid=29880). The test suite exercises live code paths and creates
PaperTrader instances with `go_live_confirmed=true`, which mutate `cfg.is_paper_trading` globally.
Because `TradeExecutor` re-read `cfg.is_paper_trading` at every decision point (15 call sites),
any post-construction mutation of that global could silently switch a running executor from paper
to live mid-process.

## Non-Obvious Design Decisions

### Freeze at construction, not injection

The fix is `self._is_paper = cfg.is_paper_trading` in `__init__`, captured once. An alternative
was to inject a boolean `is_paper: bool` parameter into `TradeExecutor.__init__` from `main.py`.
We chose the freeze-at-construction approach because:
1. It requires zero changes to `TradingBot.__init__` or any call site
2. `cfg.is_paper_trading` is already correctly set by the time `TradeExecutor` is constructed
   (PaperTrader's `_load_state()` runs in `PaperTrader.__init__` which is called before executor)
3. Injection would require threading the value through `TradingBot` and any future callers

### Belt-and-suspenders: `[LIVE_GUARD]` in `_execute_live`

`execute()` already routes to `_execute_live` only when `not self._is_paper`. The hard gate in
`_execute_live` is defense-in-depth: if the routing logic has a bug, the gate ensures live orders
are structurally impossible for paper executors. This is the fail-closed requirement.

### `_check_live_loss_limit` paper guard

Previously, if `cfg.is_paper_trading` was flipped after construction (e.g. by a test), the executor
might enter the live validation path and call `_check_live_loss_limit`. The new `if self._is_paper:
return False` guard ensures the balance is never seeded for paper executors, regardless of how the
caller got there.

### Existing tests compatible without changes

All existing tests set `cfg.is_paper_trading` BEFORE calling `TradeExecutor(rest, paper)`, so
`self._is_paper` captures the intended value at construction. No test needed updating.

## Paper-Mode Safety Verdict

After this change, a `TradeExecutor` constructed in paper mode:
- Has `self._is_paper = True` frozen for its lifetime
- Routes `execute()` to `_execute_paper` unconditionally
- Has `_execute_live` guarded with `[LIVE_GUARD]` -- returns None if called directly
- Has `_check_live_loss_limit` guarded -- returns False, never seeds balance
- Logs `[EXECUTOR_STATE] mode=paper` at construction for audit trail

Live orders are structurally impossible from a paper-mode executor. Any post-construction mutation
of `cfg.is_paper_trading` by tests or CLI commands has no effect on a running executor instance.
