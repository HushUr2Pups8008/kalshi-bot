# v0.27.2 Plan: LLM Model Mismatch Detection and Daily Review LLM Health Block

## Context

After v0.27.1 was deployed (removing `repetition_penalty` from the Ollama payload), the new
WARNING logging revealed the actual HTTP 404 error body:

```
Ollama HTTP 404 from /v1/chat/completions -- body: {"error":{"message":"model 'qwen2.5:3b' not found",...}}
```

Root cause: `config.py` had `qwen2.5:3b` as the default `OLLAMA_MODEL`, and `.env` had the
correct value (`qwen2.5:7b`) commented out. Ollama only had `qwen2.5:7b` pulled.

The startup health check at `main.py:_check_llm_health()` already logged the mismatch at INFO
level (`model=qwen2.5:3b | available=['qwen2.5:7b']`) but emitted no warning, so it was invisible
in normal operation. Every inference attempt then returned HTTP 404.

This version fixes the detection gap and makes LLM health visible in the daily review.

---

## Changes

### 1. `main.py` — Model mismatch WARNING at startup

Added after the `log.info("LLM: Ollama running | ...")` line:

```python
if models and cfg.ollama_model not in models:
    log.warning(
        "LLM: configured model '%s' not in Ollama available list %s"
        " -- every inference call will return 404;"
        " set OLLAMA_MODEL env var or run: ollama pull %s",
        cfg.ollama_model, models, cfg.ollama_model,
    )
```

With this change, the next service restart with a mismatched model emits a WARNING-level log
entry with the configured name, the available list, and the exact `ollama pull` command to fix it.

### 2. `config.py` — Default model corrected

Changed default from `qwen2.5:3b` to `qwen2.5:7b`. The 7b model is confirmed pulled and working
on this machine. The 3b default was incorrect and caused the 404 loop on every fresh deployment
where `OLLAMA_MODEL` was not explicitly set.

### 3. `scripts/daily_review.py` — LLM health block in section 3

Added 6 lines to section "3. ANALYSIS" between the existing "LLM rows" line and "Analysis
rejections total". Data sourced from `edge_stats["llm_observability"]` which is already produced
by `signal_edge_diagnostics.summarize()` — no new I/O.

Example output (pre-fix, showing the problem):
```
  LLM attempted                    : 17
  LLM result used                  : 0  (success rate: 0%)
  LLM fallback to keyword          : 17
  LLM status breakdown:
    ollama_http_error: 14
    ollama_unavailable: 3
```

Expected output post-fix (after service restart with correct model):
```
  LLM attempted                    : N
  LLM result used                  : N  (success rate: ~100%)
  LLM fallback to keyword          : 0
  LLM status breakdown:
    ollama_success: N
```

### 4. `.env` — `OLLAMA_MODEL` uncommented (local, not committed)

`# OLLAMA_MODEL=qwen2.5:7b` -> `OLLAMA_MODEL=qwen2.5:7b`. Gitignored; fixes the live service
on this machine without requiring a code change.

---

## Non-Obvious Design Decisions

- **WARNING only when models list is non-empty**: `if models and cfg.ollama_model not in models`
  avoids false-positive warnings if `api/tags` returns an empty list (Ollama starting up, empty
  install with no models pulled yet is a different state than "model pulled but wrong one").
- **Remediation command in the warning**: `ollama pull %s` is included so the operator can copy
  the exact fix from the log without looking up the model name.
- **No `.env` change committed**: The env file is gitignored and machine-specific. The correct
  fix for any machine is either to set `OLLAMA_MODEL` in `.env` or to `ollama pull` the model
  named in the default. Both are now surfaced clearly in startup logs.
